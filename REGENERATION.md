# Regenerating the DoiT fork

`github.com/doitintl/go-googlesql` is `goccy/go-googlesql` with two changes
that cannot be made in Go alone, because `googlesql.go` and the engine module
(`github.com/doitintl/googlesqlwasm2go`) are generated by goccy's
`googlesql-wasm` pipeline:

1. `(*AnalyzerOptions).SetDefaultTimeZoneName(name) error` and
   `(*AnalyzerOptions).DefaultTimeZoneName() (string, error)`, hand-written
   in `analyzer_options_doit.go`, backed by two C++ entry points in
   `regen/doit/doit_bridge.cc` (`googlesql::FindTimeZoneByName`, which is
   `absl::LoadTimeZone`, then `AnalyzerOptions::set_default_time_zone`;
   `absl::TimeZone::name()` for the getter). The generated binding cannot
   carry `absl::TimeZone` across the Wasm boundary, so its
   `SetDefaultTimeZone(*TimeZone)` sets a default-constructed zone and
   `DefaultTimeZone()` returns nothing.
2. The engine module is imported as `github.com/doitintl/googlesqlwasm2go`
   (`bridge.Wasm2GoImportPath` in `regen/wasmify.json`), so a consumer needs
   one `replace` for this module only.

Everything else is upstream: the GoogleSQL revision, the exported API, the
tool versions. The fork is rebased by replaying the overlay below on the next
upstream `googlesql-wasm` release.

## Overlay (`regen/`)

The `regen/` directory in this repository holds every file that differs from
a clean `goccy/googlesql-wasm` v0.4.0 checkout:

- `wasmify.json`: upstream's file plus `bridge.CustomBridgeSources:
  ["doit/doit_bridge.cc"]` and `bridge.Wasm2GoImportPath:
  "github.com/doitintl/googlesqlwasm2go"`.
- `doit/doit_bridge.cc`: the two exports, `w_9000_0` (set) and `w_9000_1`
  (get). Service id 9000 is reserved for DoiT additions; the generated bridge
  numbers its services from 0 in declaration order and has about 1,500.
- `doit/regen.sh`: the upstream pipeline (`make wasm` /
  `.github/workflows/build.yml`) with the serial wasi-sdk compile replayed
  in parallel by `doit/par-compile.py` from `.wasmify/wasm-build.json`
  (identical commands; wasmify then resumes from its object cache).

## Command sequence

```sh
git clone --branch v0.4.0 --recurse-submodules https://github.com/goccy/googlesql-wasm.git
cd googlesql-wasm
cp -R <go-googlesql>/regen/doit doit && cp <go-googlesql>/regen/wasmify.json wasmify.json
docker volume create wasmify-bazel-cache
docker run -d --name wasmify-doit --memory=20g --cpus=10 \
  -v "$PWD":/work -v wasmify-bazel-cache:/root/.cache/bazel -w /work \
  wasmify-local:v0.4.8-arm64 sleep infinity          # ghcr.io/goccy/wasmify:v0.4.8 on amd64
docker exec wasmify-doit bash doit/regen.sh 10        # writes pipeline.log in the checkout
```

`regen.sh` runs, in order: `wasmify build --non-interactive` (native Bazel
build under wasmify's compiler wrapper), `wasmify generate-build`, `wasmify
parse-headers`, `wasmify gen-proto`, `wasmify wasm-build --dry-run`,
`par-compile.py`, `wasmify wasm-build --optimize --non-interactive`, `buf
generate --timeout 30m`, `make bundle-gomod`. Do not run the Bazel cache on a
macOS bind mount (case-colliding paths in the extracted Python toolchain);
use the Docker volume.

Then copy the outputs into the two forks:

```sh
cp build/wasm2go/googlesql.go <go-googlesql>/googlesql.go
rsync -a --delete --exclude .git --exclude .github --exclude Makefile --exclude README.md --exclude LICENSE \
  build/wasm2go/internal/wasm2go/ <googlesqlwasm2go>/
(cd <googlesqlwasm2go> && find . -type f ! -path './.git/*' ! -name googlesql_wasm2go.sha256 | sort | xargs shasum -a 256 > googlesql_wasm2go.sha256)
(cd <go-googlesql> && shasum -a 256 googlesql.go > googlesql.go.sha256 && go test ./...)
```

Results: after substituting the module path, the regenerated bridge differs from upstream's `googlesql_wasm2go.go` release asset of googlesql-wasm v0.4.0 in one line: an extra host stub for the unresolved import `_ZN9googlesql29FieldFormat_Format_descriptorEv` (`FieldFormat::Format_descriptor()`, protobuf reflection on the `googlesql.format` field annotation, reached only through PROTO-typed catalogs). The link on this machine leaves that symbol undefined where upstream's CI run resolved it; the spike's 2026.10.3 build on the same image had the same stub and an identical corpus. A caller would get a null descriptor, so PROTO types with format annotations are out of scope for this build until the archive-member difference is found. The engine exports `Inv_9000_0` and `Inv_9000_1` in addition to upstream's set; `go test ./...` passes here, including `TestDefaultTimeZoneName`.

Checksums: `googlesql.go.sha256` here, `googlesql_wasm2go.sha256` in the engine fork (regenerated over the whole tree, as upstream's release manifest is).

## Verifying a regeneration

- `go test ./...` here: `TestDefaultTimeZoneName` proves the setter and
  getter; the upstream tests prove the rest of the surface is unchanged.
- `make verify` in both forks checks the committed checksums.
- In Offramp, the recorded corpus (`make corpus-replay`, suites analyze,
  tpch, tpcds) must stay green: that is the proof the regenerated analyzer
  resolves every recorded statement as the previous one did.
